# A18 分批识别、两段式写作与 strict schema 落盘

## 1. 背景

三条用户决策同时落地：

1. 两段式写作（英文草稿 → 中文译写），链路是「识别英文 → 整理 → 打草稿 → 译成中文 md」；
2. `normalize` / `evidence` 明确禁止翻译，`quote` 必须逐字取自 IR；
3. 识别改分批，避免 50 页材料一次性塞进单个 turn。

同时修复了真实调用暴露的硬阻塞：`recognition` / `document_ir` 两份 schema 是空壳，
供应商 strict structured output 直接拒绝请求（`additionalProperties` 必须为 false）。

## 2. 改动清单

| 文件 | 改动 |
|---|---|
| `schemas/recognition.schema.json` | 按 SKILL.md v1.1.0 写实：`pages[].blocks[]` 含 `block_id`/`text`/`region`；全部 object `additionalProperties:false`、`required` 全覆盖；`region` 归一化 0–1 且可 null；删除 `raw_text` |
| `schemas/document_ir.schema.json` | 同上；`source` 定为 `path_name`/`page_count`/`sha256` 三键可空；`pages` 只留 `page_number` |
| `schemas/evidence.schema.json` | 1.0.0 → 1.0.1：`value_text`/`region` 改为 required + null，`oneOf` → `anyOf`；字段未增删 |
| `pipeline/schema_loader.py` | 登记三份版本；新增 `MODEL_OUTPUT_SCHEMAS` 与 `_strict_issues`，加载时递归检查 strict 三条规则，不合规立即 `SCHEMA_INVALID`(4) |
| `pipeline/stages/recognize.py` | 每 5 页一次调用（`BATCH_PAGES`），逐批校验页覆盖后合并；覆盖不符抛 `MODEL_INVALID_JSON`(5) |
| `pipeline/writer.py` | 两段式：`writer` 产出英文 → `draft_en.md`；`translate` 产出中文 → `draft.md`；prompt 先加载后读 evidence（保持 I4 的失败顺序） |
| `pipeline/stages/write.py` | `PRODUCES` 增加 `draft_en` |
| `prompts/normalize.md`、`prompts/evidence.md` | 1.0.0 → 1.0.1：明确禁止翻译、`quote` 逐字取 IR 连续片段 |
| 5 个工程夹具 + `tests/fixtures/quality/*` | 迁移到 strict 结构（`document_ir.source` 三键、facts 增加 `region`/`value_text`），`validation.json` 重生成 |
| 测试 | recognize 分批与覆盖失败、writer 两段式与 translate 缺失、strict 规则回归；`FakeProvider` 支持按请求生成页 |

## 3. 验收原文

```text
$ ../venv/Scripts/python.exe -m pytest -q
201 passed in 4.61s
exit=0

$ ../venv/Scripts/python.exe -m compileall -q pipeline
exit=0
```

strict 检查的确定性证据（`test_model_output_schemas_are_strict_compatible`）：
三份模型输出 schema 的 `_strict_issues(...)` 均返回空列表；
反例 `{"type":"object","properties":{...}}` 会报 `additionalProperties`，
`required` 缺项会报 `missing: b`，`oneOf` 会报不支持。

## 4. 行为变化（下游必读）

1. **一次识别 = N 次调用**：`ceil(页数/5)`。50 页材料是 10 次，单次 120s 上限，串行耗时随之上升。
2. **`recognition.json` 只有 `pages`**：`raw_text` 已移除，合并后按 `page_number` 升序。
3. **页覆盖不符即失败**：某批返回的页号集合不等于请求集合 → `MODEL_INVALID_JSON`(5)，不会静默补页。
4. **`write` 阶段两次模型调用**：manifest 的 `model_calls` 记为两条（`writer`、`translate`），
   `PRODUCES` 变为 `draft` + `draft_en`，I2 目录新增 `draft_en.md`。
5. **`translate` 缺失即失败**：`ASSET_MISSING`(8)，且英文草稿已保留在 `draft_en.md`，便于排查。

## 5. 风险与未覆盖项

1. **`prompts/translate.md` 尚未交付**（B 的资产）。代码已就绪，真实 run 会在写阶段以
   `ASSET_MISSING` 停下；工程测试用 `stub_prompts/translate.md` 覆盖。
2. **`region` 的 0–1 约定只在 schema 与 SKILL.md 层**，尚未有"坐标是否落在页内"的交叉校验；
   A14 若做，建议同时校验 `region` 与 `document_ir.blocks[].region` 一致。
3. **`block_id` 交叉存在性未校验**（见 I3 当前待办），仍属 A14。
4. **分批的批次大小写死 5 页**，未做成配置项；页数极多的材料若仍超时，需要按 token 预算调整。
5. **两段式使写作成本翻倍**，且英文草稿不参与校验；若译写阶段改动了数字，仍由
   `NUMBER_MISMATCH`（A14 实现后）在中文稿上兜住。

## 6. 真实调用实测（MED-04，5 页）

```text
python main.py run ../materials/ges_docs_MED-04.pdf --material-id MED-04 --stage recognize
exit=0，recognize 688248 ms（11m28s），run_id 07b1596f…
recognition.json：pages=5，page_number=[1..5]，blocks=[17,21,39,35,15] 共 127 块
schema 校验：0 处不合规；127/127 块都有归一化 region；空 text 块 = 0
validate_run：valid=false，唯一 code = ASSET_MISSING（无 draft/final，符合预期）
```

调参过程（全部有实测支撑，不是猜的）：

| 批次 | 超时 | 结果 |
|---|---|---|
| 5 页/批 | 120s | `MODEL_TRUNCATED`：单页就要约 100s，5 页必然超时（schema 已通过，失败点已后移） |
| 2 页/批 | 300s | `MODEL_TRUNCATED`：两页超过 300s |
| 1 页/批 | 300s | 成功，5 页共 11m28s，约 138s/页 |

因此 `BATCH_PAGES = 1`、`config.json` 的 `vision.timeout_s` 改为 300。代价是
**50 页的 BIO-02 约需 1.9 小时**，四份材料合计约 4 小时纯识别时间；这是当前最大的进度风险。
