# 科普文档自动生成工具 · 运行说明

本目录是参赛作品的源码部分，负责把组委会下发的专业材料转换为符合提交要求的
Markdown 科普文档，并完成自检与打包。

赛项编号：BRICS2026-ST-003（人工智能大模型产业开发与应用 · 预选赛）

---

## 一、它解决什么问题

赛项要求提交的 `.md` 文档**必须由提交的代码生成**，不能手写。本工具就是这条
生成链路：读取 `materials/` 里的原始材料 → 抽取文本 → 生成结构化科普文档 →
写入 `docs/` → 自检 → 打包成一个压缩包。

同时满足以下硬性约束：

| 要求 | 实现位置 |
| --- | --- |
| 每份材料对应 1 份 `.md`，含标题 / 引言 / 正文 / 总结 | `pipeline/prompts.py`、`pipeline/generate.py` |
| 文末注明对应材料编号及原文来源 | `pipeline/prompts.py::PROVENANCE_TEMPLATE` |
| 源码目录命名 `source_code`，含源码 + 依赖 + 运行说明 | 当前目录结构 |
| 不得出现真实 API Key，须从环境变量读取 | `pipeline/generate.py::LLMClient._api_key` |
| 打包为一个压缩包，不得拆分 | `pipeline/package.py` |

---

## 二、环境要求

- Python 3.9 及以上（开发与测试环境为 3.10 / 3.11）
- 无需 GPU
- 可选依赖见 `requirements.txt`

```bash
cd source_code
pip install -r requirements.txt
```

`txt / md / html / docx` 四种材料格式仅用标准库即可解析；只有读取 PDF 材料时才
需要额外安装 `pypdf`。

## 三、目录结构

```
preselect-2026/
├── materials/            原始专业材料（自行放入，不提交）
├── docs/                 生成的科普文档（提交）
└── source_code/          本目录：程序源码（提交）
    ├── main.py           命令行入口
    ├── config.json       运行配置（服务商预设在此）
    ├── requirements.txt  依赖配置
    ├── README.md         本文件
    ├── .env              本地密钥（不提交，打包自动排除）
    ├── .env.example      密钥配置模板
    ├── tests/
    │   └── test_pipeline.py  单元测试
    └── pipeline/
        ├── extractors.py 材料文本抽取
        ├── prompts.py    提示词模板
        ├── generate.py   生成引擎与文档组装
        ├── review.py     质量评审（数字核对 + 维度打分）

        └── package.py    打包与结构校验
```

## 四、使用步骤

### 0. 环境体检（建议每次开跑前先做，约 5 秒）

```bash
python main.py doctor
```

逐项确认：Python 版本、`requests` / `pypdf`、`.env` 是否读到、服务商预设解析结果、
密钥是否设置、接口是否**真的连得通**、材料与文档数量、源码目录命名、打包是否排除 `.env`。

**唯一允许出现「注意」的项是密钥未填**，那意味着走离线引擎、文笔打折；
出现「错误」则必须先修，否则生成或打包会失败。

### 1. 放入材料

把组委会提供的专业材料放进 `materials/`。文件名建议保留材料编号前缀，
程序会据此推断材料编号：组委会命名形如 `ges_docs_AI-01.pdf` → 编号 `AI-01`
（文档将命名为 `AI-01.md`）；普通命名如 `M03_xxx.pdf` → `M03`；推断不出时
按序号 `M01`、`M02` 排列。

想先看看输出长什么样，可把根目录 `示例材料/` 里的两份演示材料复制进来跑一遍，
看完用 `rm -f ../materials/*`（Windows：`del ..\materials\*`）清空再放真实材料。

### 2. 配置生成引擎（可选）

**不配也能跑。** `llm.preset` 为空时程序使用离线抽取式引擎，不联网、不要密钥，
产出结构合规但文笔平实。想提升「科普表达」这一项，做两步即可。

**① 选一家服务商**——`config.json` 里改一个词：

```json
"llm": { "preset": "deepseek" }
```

内置预设（接口均已实测可达）：

| preset | 服务商 | 默认模型 |
| --- | --- | --- |
| `mixtk` | 第三方中转站 | gpt-6.1-sol |
| `deepseek` | DeepSeek | deepseek-chat |
| `dashscope` | 阿里云百炼（通义） | qwen-plus |
| `zhipu` | 智谱 | glm-4-flash |
| `moonshot` | 月之暗面 | moonshot-v1-8k |

中转站的模型名由平台自定义，换模型时以其「模型列表」页显示的名称为准。

接自建服务或代理时，直接填 `base_url` / `model`，优先级高于预设。

**② 把密钥填进 `source_code/.env`**：

```
LLM_API_KEY=sk-你的密钥
```

程序启动时会自动读取该文件；**已存在的系统环境变量优先**，不会被文件覆盖，
方便临时排查。`.env` 在打包时自动排除，不会进入提交包。

也可以改用系统环境变量（二者选一）：

```bash
# Linux / macOS
export LLM_API_KEY="你的密钥"

# Windows PowerShell
$env:LLM_API_KEY = "你的密钥"
```

密钥**任何情况下都不写进 config.json 或源码**——赛项规定出现真实密钥即判违规。

若材料来源名称与文件名不一致，可在 `config.json` 的 `document.overrides` 中逐份指定；
英文文献的 PDF 首行常是期刊页眉，可同时用 `title` 指定文章标题（否则会被误当成标题）：

```json
"overrides": {
  "AI-01": {
    "title": "文章标题",
    "source": "作者等. 论文题目. 期刊 年份, 卷(期): 页码. DOI: ..."
  }
}
```

### 3. 生成文档

```bash
python main.py generate
```

输出示例：

```
[引擎] llm  ->  https://api.deepseek.com/v1  model=deepseek-chat
[输入] 共 3 份材料

(1/3) ges_docs_AI-01.pdf  ->  AI-01
    已生成 AI-01.md（4821 字符）
...
完成：3 份文档 -> .../docs
```

长材料（超过 20000 字符）会自动走 map-reduce：先分片提炼要点，再合写成文，
避免超出上下文窗口导致信息丢失。

### 4. 质量评审（判断作品好坏，约 40 秒/份）

```bash
python main.py review
```

自检只回答"格式合不合规"，不回答"文章写得好不好"。`review` 补上后者，分两层：

**第一层：数字核对（不联网，瞬间完成）**
把文档里出现的每个数值拿去原始材料里找，分三类报告：一致 / 近似（四舍五入）/
原文找不到。"原文找不到"就是模型编造或篡改了数据，**这类问题人眼几乎发现不了，
但科学准确性是底线**。实测能拦住三种情况：篡改（56.1% 写成 63.8%）、凭空编造
（多出"47 万个像元"）、四舍五入（0.87 写成 0.9，归为近似不算错）。

个位数（1-9）和标题里的章节序号会被跳过，否则报告里全是噪声。

**第二层：维度打分（需要大模型）**
按科学准确性 / 科普表达 / 内容完整性 / 格式规范性四个维度打分，并要求评委
**引用原文句子**举出具体问题，避免只给一句"写得不错"。输出示例：

```
    科学准确性      12/15
    科普表达       16/20
    内容完整性      18/20
    格式规范性      10/10
    小计         56/65
```

另外会统计篇幅、段落数、小节数，以及"也就是说""可以理解为"这类通俗解释标记的
出现次数——可作为"有没有真的在解释"的粗略参考。

**怎么读这个分数**：它是模拟评审，不是官方评分，只能看趋势和找具体问题，
不要把 56/65 当成最终成绩。真正有价值的是它挑出的那句具体问题。

### 5. 提交前自检

```bash
python main.py validate
```

会逐项检查文档结构、溯源字段、材料与文档数量是否一一对应、源码目录命名、
依赖与说明文件是否齐全、以及全库敏感凭证扫描。出现「错误」必须修复后才能提交。

### 6. 打包

```bash
python main.py package
```

生成 `作品.zip`，顶层直接是 `.md` 文档与 `source_code/`，不套多余文件夹。
打包后会读回压缩包索引，确认入口文件、依赖配置、运行说明都在包内。

也可以用一条命令跑完三步：

```bash
python main.py all
```

重复运行时，程序会先清掉 `docs/` 里上一轮生成的文档，避免换材料后残留旧文件、
导致"文档比材料多"或把过期文档一起交上去。

### 7. 跑测试（可选）

```bash
python -m unittest discover -s tests -v
```

54 项测试覆盖编码识别、docx/html 解析、小标题剥离、长材料切分、章节缺失兜底、
密钥扫描、`.env` 解析（含 BOM / 引号 / 空值）、服务商预设解析、
数值核对（篡改 / 编造 / 四舍五入）、以及「鉴权失败不重试」等容易在赛场上翻车的环节。

## 五、两种生成引擎的差别

| | `llm` 引擎 | `extractive` 引擎 |
| --- | --- | --- |
| 是否需要网络 | 需要 | 不需要 |
| 是否需要密钥 | 需要 | 不需要 |
| 输出质量 | 可读性好，适合科普表达 | 结构合规、忠于原文，但文笔平实 |
| 适用场景 | 正常备赛 | 断网、密钥失效时的兜底 |

`llm` 调用失败时会自动回退到 `extractive`，保证流水线不会中断。

**实测耗时**（单份材料）：材料 ≤ 20000 字时一次调用完成，约 40–50 秒；
超过 20000 字时自动按 10000 字分片，先逐片提炼要点再合写。若赛题材料较多，
可先按材料份数预估总耗时，再决定是否需要提前一晚开跑。

长材料的处理方式：`SINGLE_CALL_LIMIT`（20000 字）以内直接单次生成；超过则用
`CHUNK_SIZE`（10000 字）切分，`MAP_PROMPT` 逐片提炼事实要点，`REDUCE_PROMPT`
汇总成文。这样避免超长上下文导致中段信息被模型忽略。

## 六、准确性保障机制

科普表达得分与科学准确性是两个独立维度，但后者是一票否决式的底线。代码层面
用三道措施守住：

1. **抽取阶段不改写**。`extractors.py` 只做格式转换与空白规整，不做任何同义
   替换或概括，原文数字与限定条件原样保留。
2. **提示词硬约束**。`prompts.py` 的 SYSTEM 段落明确禁止虚构文献、禁止改变
   研究结论与适用范围、禁止补全原文未交代的内容。
3. **溯源可核验**。每份文档末尾写入材料编号、原文来源、原文内容 sha256 指纹
   与生成时间，可逐份回溯到原始材料。

## 七、常见问题

**Q：提示「可能是扫描件（图片型 PDF）」怎么办？**
材料是图片型 PDF，需要先 OCR 转成可复制文本，再放入 `materials/`。

**Q：生成的中文出现乱码？**
`extractors.py` 会依次尝试 UTF-8 / GB18030 / UTF-16 解码。若仍乱码，说明源文件
编码特殊，请另存为 UTF-8 后重试。

**Q：填了密钥却提示「环境变量未设置」？**
程序会读取 `source_code/.env`，但要满足两个条件：文件名恰好是 `.env`（不是
`.env.txt`），且写成 `LLM_API_KEY=值` 的形式。值留空会被当作未设置，
这是为了避免空密钥换来一个看不懂的 401。改完运行 `python main.py doctor` 确认。

**Q：密钥是第三方中转站（聚合平台）发的，能用吗？**
能，但**地址必须跟着换**。中转站的密钥配官方地址、或官方密钥配中转站地址，
两边都会返回 401，很容易被误判成密钥过期。此时把 `config.json` 的 `llm` 段
改成该平台文档给出的那一组：

```json
"llm": {
  "preset": "",
  "base_url": "https://该平台的接口地址/v1",
  "model": "该平台模型列表里的名字"
}
```

`base_url` 末尾一般到 `/v1` 为止（程序会自动拼 `/chat/completions`）。
模型名必须与平台文档完全一致，`gpt-4o-mini` 和 `gpt-4o mini` 是两个不同的名字。
改完运行 `python main.py doctor`，它会真实发一次请求来确认三者匹配。

需要提醒的是：中转站的可用性、模型真伪、限流策略都由第三方决定，赛前务必实测；
一旦它失效，程序会自动回退到离线引擎、不会中断，但「科普表达」这一项会打折。

**Q：会不会把自己的密钥打进提交包？**
不会。密钥只从环境变量或 `.env` 读取，`.env` 在打包时被显式排除，
`.env.example` 里只有空占位；`validate` 还会做一次全库密钥扫描作为兜底。

**Q：终端提示「以下 N 个文件格式不支持，已被忽略」？**
说明 `materials/` 里混进了 `xlsx`、`pptx`、`doc` 等格式。这类文件不会被静默丢掉，
但也不会生成文档。若它们确实是赛题材料，请先另存为 pdf / docx / txt 再重跑，
否则提交的文档数会少于材料数，直接影响「一一对应」这一项。

**Q：某份材料报「内容为空」或「可能是扫描件」？**
空文件直接补内容；扫描件 PDF 没有文字层，需要先 OCR 转成可复制文本。

**Q：想调整文档篇幅或章节？**
篇幅改 `config.json` 的 `document.target_words`；章节结构改 `prompts.py` 中的
`DOC_PROMPT`。改完重新执行 `generate` 即可。
